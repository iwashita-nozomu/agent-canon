## Purpose / Use When

予備知識のない状態からレポジトリ全体を読み、何を提供し、どう動き、どの契約と
実装・検証で成り立つかを正確に理解するために使います。前段で得た知識を使って次を
理解できる順序を選び、その理解を判断するモデルの現在の context に積み上げます。
未知のレポに入ったときの入口把握は [repo-onboarding](repo-onboarding.md) が所有します。

## 予備知識なしからの標準読取順

まず対象 root、branch / revision、ローカル差分と要求範囲を確認し、次の順で読みます。
各段階で得た全体像・用語・契約を context に置いてから、それを前提とする本文へ進みます。

1. **適用する指示を読む**。root の AGENTS.md などから、正本の所在、読取境界、
   repository 固有の規約を把握します。各 subtree の指示はそこへ入る前に読みます。
   関連 Issue や途中作業があれば、その要求と current source を照合します。
2. **構成と入口を掴む**。root README、文書・directory の索引、実際のファイル一覧、
   manifest、build / run 設定を読みます。レポの目的、主要な成果物、module の区分、
   ソース・テスト・文書・生成物の所在、公開 API / CLI / service の入口を掴みます。
   入口や役割は実際の登録・参照から確認します。
3. **要求と外から見た振る舞いを読む**。要求・設計の概要、公開 API の説明、利用例、
   代表的なテストと実際の呼出元を読みます。何を入力し、API が何を作用させ、何を
   保証するかを押さえます。この期待挙動を、その後の実装を理解する基準にします。
4. **共通の概念と契約を読む**。前段で現れた用語の定義、共通の型・schema、domain
   model、状態と所有、有効領域、失敗時の契約を読みます。主要なデータと境界の意味を
   揃え、module の名前から責務を推測せずに処理経路を読める状態にします。
5. **主要な処理経路を入口から辿る**。基本的な利用例の入力から出力まで、entrypoint、
   orchestration、module 間の呼出しとデータ・状態の移動を辿ります。まず公開境界と
   呼出関係を押さえ、レポ全体がどう機能を組み合わせているかを掴みます。複数の独立した
   入口・機能群がある場合は、それぞれの主要経路を確認します。
6. **依存順に module 内部を精読する**。前段で得た依存関係に沿い、共通の型・基盤・
   提供側の実装から、それを利用する側へ進みます。各 module の契約、実装、対応する
   テストを照合し、入力の仮定から API の作用を経て性質が保証される仕組みを読みます。
   依存先の保証が利用側の仮定を満たすかも確認します。循環する部分はまとまりとして
   往復して読みます。内部を読んだ後は主要経路へ戻り、部品を組み合わせた結果を
   外部契約と照合します。
7. **検証と実行の条件を読む**。残りのテスト・fixture、test runner、CI、環境設定、
   運用・補助ツールを読みます。どの条件・性質が検証され、何が未検証か、実際の実行に
   どの設定が効くかを把握します。先に読んだ本文は、矛盾や変更がなければ再利用します。
8. **残りを読み、全体像を照合する**。未読の module、別経路、文書、例、移行資料、
   隠し設定、索引にないファイルを読みます。最初の構成・要求と、実装から分かった
   依存・契約・検証を照合し、全体像を更新します。食い違いは根拠のある未解決事項として
   残し、説明の辻褄を合わせるために契約を補いません。

入口から辿る段階では機能の組合せを、内部精読では各部の成立条件を理解します。
未知の概念や依存が次の本文の理解を妨げる場合は、その定義・契約を先に読み、元の経路へ
戻ります。既存の依存情報を再利用し、解けない依存には
[dependency-analysis](dependency-analysis.md) の該当手段を使います。

## 読んだ契約を現在の context に積み上げる

全体の責務・依存の見取り図に、読んだ境界の契約を結び付けます。次の読解・判断に効く
内容は、低 Effort の担当にも必要な本文が見えるよう、現在の context に揃えます。

- 契約の owner、API / 型、根拠の path と節・symbol、読んだ版とローカル差分。
- 入力の仮定・有効領域、API の作用と結果・保証、状態・所有・失敗時の条件。
- 提供側の保証と利用側の仮定の対応、テストの入力準備・API 呼出し・確認する性質。
- 要求として定まった契約、実装の観察、推測、未確定・食い違いの区別。

引き継ぎでは受信モデルの prompt に必要な契約本文を含めるか、そのモデル自身が読んで
取り込みます。圧縮・再開後も現在見える本文を確認し、欠けた仮定や保証は source や
保存した map から読んで戻してから、その条件に依存する読解・判断を進めます。
保存先や過去の読了だけでは、現在の context に本文があることを保証しません。
source の版が変われば照合し直し、収まらなければ作業単位を分けて必要な境界条件を渡します。

## 読取漏れと再開を支える

構成を掴む段階で、既存の inventory から本文読取の対象を列挙します。Git なら
`git ls-files -z --cached --others --exclude-standard` と `git status --short --ignored`、Git がなければ
`rg --files --hidden` などを使い、列挙手段の除外規則も確認します。ソース・文書・テスト・
設定・隠しファイル・CI・補助ツールを含め、現在の話題との関連の薄さだけで落としません。
ignored、generated、vendor、binary、symlink、nested repository / submodule の扱いを
明示し、生成元で代表させた内容や取得できない内容は、本文読了へ数えません。
認証情報の値を収集・表示せず、ファイルの役割を確認します。

列挙・検索 hit・要約と本文の読了を区別し、長い本文は範囲を分けて読みます。
出力切れは見えた範囲だけを読了とします。既存の task record に版・path・読了範囲と
未読・阻害・除外を残せば、中断や分担後の続きから再開できます。記録した契約マップも
context の読み戻しに使います。再開時と完了前には差分と一覧を照合し、追加・変更された
内容と影響する理解を更新します。未読・未確認が残れば、その範囲と再開条件を示します。

## 出力と完了条件

レポが提供する機能、主要経路、module の責務と依存、契約が実装・検証でどう成立するかを、
根拠に結び付けて説明できる状態にします。全体像と次の判断に必要な契約は現在の context
に載せ、読了範囲・除外・未解決の食い違いを添えます。

対象の本文を読み終えた範囲を報告し、除外を含めて全レポ読了とは扱いません。
読取の依頼だけで修正、テスト実行、環境構築を開始しません。追加作業の判断は
[agent-orchestration](agent-orchestration.md#decision-order) に従います。
