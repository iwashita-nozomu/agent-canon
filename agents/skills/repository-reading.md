## Purpose / Use When

レポジトリ全体を読み、構成・契約・実装のつながりを把握する依頼に使います。
読む順序と本文の読了範囲を管理し、索引にないファイルも拾います。
境界ごとの契約マップを作り、低 Effort の担当や context 圧縮後にも契約を正確に渡します。
未知のレポに入ったときの入口把握は [repo-onboarding](repo-onboarding.md) が所有します。

## 対象を列挙する

1. 対象 root、branch / revision、作業中の差分、要求された範囲を確認します。
   関連 Issue や途中作業がある場合は、既存の continuation evidence を引き継ぎます。
2. 既存の inventory から対象ファイルを列挙します。Git では
   `git ls-files -z --cached --others --exclude-standard` で tracked と未追跡ファイルを
   把握し、`git status --short --ignored` と ignore 設定から対象外の領域を確認します。
   Git がなければ `rg --files --hidden` など、利用可能な列挙手段とその除外規則を使います。
   README、検索結果、既存の owner map と実際のファイル一覧を照合します。
3. 全体読取では、ソース、文書、テスト・fixture、設定、隠しファイル、CI、補助ツールを
   母集団に含めます。現在の話題との関連の薄さだけで未読ファイルを落としません。
   ignored、generated、vendor、binary、symlink、nested repository / submodule は
   種別と扱う範囲を記録します。生成元・参照先・入手可能な形式を確認し、読取対象と
   除外を区別します。認証情報の値を収集・表示せず、そのファイルの役割だけ確認します。
   対象内で取得できない内容は未確認として残します。

この inventory を読了確認の母集団にします。既存の task record や簡単な一覧に、path、
読んだ版・範囲、状態と未読理由を残せば十分です。専用 walker や固定 schema は要求しません。

## 読む順序

次の順序を基本に、実際の契約・依存関係で前後させます。各段階で見つけた参照先を
一覧へ照合し、残りのファイルにも順番を割り当てます。

1. **指示と全体像**: root と対象 subtree の適用指示、README、構成の索引を読みます。
   manifest、build / run 設定、entrypoint から、何を提供し、どう起動するレポかを掴みます。
2. **要求と外部契約**: 要求・設計、公開 API、型・schema、主要な呼出元を読みます。
   対応するテストも開き、入力の仮定、実際に作用させる API、確認する性質を押さえます。
3. **実装のつながり**: 共通の型・基盤から依存するモジュールへ進み、entrypoint からの
   主要な呼出しとデータの流れを辿ります。各モジュールの入力・出力・責務と、既存機能を
   組み合わせる箇所を記録します。循環する部分は一まとまりとして往復して読みます。
   依存情報が不足する箇所は import / call / reference を確認し、仮の順序を更新します。
4. **検証と実行経路**: 未読のテスト・fixture と test runner、CI、環境設定、運用・補助
   ツールの全文を読み、実装の保証と検証条件を照合します。契約の把握に先に読んだテストは
   読了範囲を再利用します。
5. **残りを閉じる**: 文書、例、移行資料、隠し設定を含む未読一覧を処理します。
   索引・リンク・参照に現れないファイルも読み、一覧との突き合わせで漏れを確認します。

各 subtree に入る前に適用指示を確認します。既存の依存情報を再利用し、判断に必要な
依存が解けない場合は [dependency-analysis](dependency-analysis.md) の該当手段を使います。
読取の依頼だけで修正、テスト実行、環境構築を開始しません。見つけた不整合は根拠と
影響を記録し、追加作業の判断は [agent-orchestration](agent-orchestration.md#decision-order)
に従います。

## 契約マップを作る

契約と実装を読む過程で、公開 API と module 間の境界を既存の task record にまとめます。
各境界について、次を本文で明示します。

- 契約の owner、対象 API / 型、根拠の path と節・symbol、読んだ revision とローカル差分。
- 呼出側が用意する入力・仮定・有効領域、API が行う作用、返す結果・保証。
  状態の所有・変更、失敗時の挙動、維持すべき不変条件も、契約にある内容を保持します。
- 依存先に要求する保証と、呼出元へ渡す保証の対応。条件を満たして機能を組み合わせられるか。
- 対応するテストの入力準備、実際の API 呼出し、確認する性質と根拠の所在。
- 未確定の契約、要求・設計・実装・テスト間の食い違いと、それを確かめる次の source。

要求として定まった契約、現行実装の観察、推測を区別します。契約の空欄を実装都合で
補ったり、private な命名・配置を拘束条件に加えたりしません。map を根拠 source と
照合し、仮定から作用を経て保証へ至る対応と、依存境界の条件に抜けがないか確認します。

## 圧縮・引き継ぎ後の context

契約マップと読了一覧を task record に残し、次の作業単位に必要な契約の本文を
handoff / 再開 context に含めます。map 全体への参照とともに、対象境界と直接の依存先・
呼出元に関する条件を展開します。低 Effort の担当にも、path や抽象的な要約だけから
契約の仮定・作用・保証を再推測させない形にします。

圧縮前に、対象と版、合意済みの結果・範囲、必要な契約、読了と未読、未解決の食い違い、
次の読取を保存します。意味を変える有効領域、失敗条件、状態・所有、保証の条件節は
圧縮後の本文にも保持します。収まらない場合は作業単位を分け、各単位の境界条件を渡します。

圧縮・再開・引き継ぎ後は、その context と保存した map を照合します。必要な契約が
欠けていれば本文を戻し、source の版や差分が変わっていれば map と読了範囲を更新してから
依存する判断へ進みます。実際に渡した範囲と残る未確認を記録します。

## 本文の読了と再開

- ファイル名の列挙、検索 hit、索引や要約の読取を、本文の読了へ置き換えません。
  長いファイルは節・行範囲などで分割し、全文の範囲が繋がるまで未読を残します。
  tool 出力が切れた場合は、表示された範囲だけを読了とします。
- 読了、部分読了・未読、阻害、除外を区別します。生成物を生成元で代表させた場合も、
  その生成物の本文を読んだとは数えず、対応する生成元と除外理由を残します。
  symlink や nested repository の境界を越える対象は、所在と読取範囲を明示します。
- 分担を選ぶ場合は、各担当の正確な path / 範囲と実際の読了結果を集約します。
  依頼済みという状態を読了にせず、担当間の漏れと重複を母集団で照合します。
- 中断・context 更新の前に、inventory、読んだ版と範囲、未読・阻害・除外、判明した
  module 間のつながり、次に読む場所を既存の task record に残します。再開時はその記録と
  現在の差分を照合し、変わったファイルと影響する読解を更新します。
- 完了前に inventory と差分を再確認します。追加・変更された内容の読取を補い、削除された
  ファイルを現在の母集団から外します。変化を追えない範囲は未確認とします。

## 出力と完了条件

レポの目的、主要な module と依存・データの流れ、契約マップと検証の対応を短くまとめます。
対象 root / revision とローカル差分、列挙方法、読了範囲、除外した内容と理由、未読・阻害、
次の読取場所を添えます。件数を示す場合は inventory の母数と各状態の内訳を一致させます。

対象とした全ファイルの本文を読み終えたときに、その範囲の読了を報告します。
未読や阻害があれば継続し、読めない理由と再開条件を残します。除外がある場合は
「全レポ読了」と一括せず、読んだ範囲と除外範囲を示します。
