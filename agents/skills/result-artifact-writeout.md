## Reader Map

- Purpose: explains how to preserve tool, hook, eval, experiment, review, and
  CI results as reusable artifacts instead of chat-only summaries.
- Use When: result saving, export, report generation, accumulated evals, or
  experiment evidence needs durable placement.
- Section path: Purpose and Use When define scope; Ownership Contract and No
  fixed artifact inventory define what is written; Destination Rules and
  Required Shape guide the selected workflow; Closeout Tokens names completion
  evidence when a structured handoff is needed.
- Boundary: generated reports are evidence artifacts, not policy truth.

## Purpose

tool、hook、eval、experiment、review、CI の結果を、あとから再利用できる
必要な artifact として書き出すための skill です。選択された出力とその
summary がある場合は、同じ source result に結び付けます。

## Ownership Contract

Persist concrete outputs without inventing a second experiment, report, or publication state. For each selected artifact that actually exists, record its parent result/run reference, path, semantic role, content checksum or equivalent immutable identity, producer/source reference when needed, destination, and successful readback. Do not overwrite different bytes at the same identity; identical replay may be treated as idempotent.

For structured artifacts, validate the saved readback with the existing parser
or consumer to confirm format validity as well as byte identity.

Preserve a raw machine-readable result, summary, or manifest only when the
producer or request selects it. If a manifest is created, include provenance
available from the run, such as command, inputs, revision, runtime, timestamps,
exit status, and schema version.

For experiment artifacts, follow the explicit disposition in
[retention](retention.md). A failed run's status alone does not determine
whether its existing evidence is written out or removed.

## No fixed artifact inventory

Enumerate only files actually generated by the selected producer. Producer-specific protocols may declare required outputs, but a generic writeout must not require summaries, case records, notebooks, plots, logs, reports, or manifest entries that were never selected. Saving a local artifact does not imply a Git branch or remote publication; use the explicit publication route owned by the selected artifact's owner.

## Use When

- user が結果の保存、書き出し、export、report、表、JSON / JSONL / Markdown 化を求める
- tool / checker / hook / skill eval の結果を次の改善 branch が読む必要がある
- experiment result と reader-facing report を同じ run から作る
- prose graph projection、diagnostics、explanation、integration plan、rewrite packet を同じ source DB から書き出す
- 既存 result を上書きせず、unique ID 付きで蓄積したい

## Destination Rules

- run-local task evidence: `reports/agents/<run-id>/`
- selected immutable agent report snapshot:
  `.agent-canon/log-archive/agent-reports/<stable-source-repository-id>/<run-id>/<snapshot-id>/`
  on the policy-owned stable branch; discover route-specific paths with
  `python3 tools/runtime/archive/runtime_log_archive_git.py status` when needed.
- accumulated skill / workflow eval: `.agent-canon/log-archive/eval-results/<eval-family>/<unique-id>.md`
- hook result chronology:
  `.agent-canon/log-archive/hook-runs/<stable-source-repository-id>/<runtime-namespace>/<hook-name>-<agent-canon-commit>.jsonl`
- experiment result artifacts: `experiments/<topic>/result/<run-id>/`; persist only producer-selected files that actually exist, with role/checksum/readback evidence.
- experiment reader report: `experiments/<topic>/report/<run-id>.md`; create it only when the request activates `report-writing`.
- formal experiment result archive: `experiments/<topic>/result/<run-id>.tar.gz` in the configured annex worktree. Retain only with `python3 -m tools.experiments.artifacts.save_experiment_result_annex --result-dir experiments/<topic>/result/<run-id> --annex-repo "$EXPERIMENT_RESULT_ANNEX_REPO"` after lifecycle and artifact evidence are complete.
- generated triage report: `reports/<tool-or-task>/`

Do not store generated reports as policy truth. If a report changes a rule, edit
the canonical workflow, skill, document, or tool and cite the result artifact as
evidence.

## Required Shape

1. Select only outputs requested by the user or required by the chosen producer,
   and choose a destination matching their owner and retention need.
2. When raw output is selected, preserve it before deriving any summary. Derive
   tables and Markdown from that same result; do not rerun a checker only for
   presentation. For prose-graph outputs, keep selected projections and
   handoffs tied to their source SQLite DB.
3. Keep failed, skipped, blocked, and partial non-experiment results. For
   experiment artifacts, a failure status alone does not decide retention; use
   [retention](retention.md). The lifecycle owner controls experiment run
   identity, terminal status, and restart decisions; retention chooses the
   applicable disposition. Use the annex archive only when archive is selected
   and requested; the source checkout remains unchanged.
4. Use unique paths or append-only JSONL for repeated results. Include stable
   grouping information available from the source, such as status, exit code,
   input fingerprint, runtime namespace, branch, commit, and tool or hook name.
5. If an individual agent report is selected for cross-run retention, use the
   existing immutable snapshot route:
   `./bootstrap.sh --control-parent-root <control-parent-root> exec --root <registered-source-root> -- python3 tools/runtime/archive/runtime_log_archive_git.py archive-agent-report --report-dir reports/agents/<run-id>`
   followed by
   `./bootstrap.sh --control-parent-root <control-parent-root> exec --root <registered-source-root> -- python3 tools/runtime/archive/runtime_log_archive_git.py push`.
   The archive tool owns its snapshot manifest and `index.jsonl`; do not rewrite
   them manually. Use broad
   `python3 tools/runtime/archive/runtime_log_archive_git.py sync` only when
   intentionally collecting accumulated runtime families such as hook JSONL or
   Codex runtime summaries, not as the default route for an individual report.
6. If a reader-facing report is requested, also use `report-writing` for its
   interpretation, limitations, and next action; this skill owns artifact
   writeout, not an experiment or report wrapper. Add `html-output` only when
   HTML is requested. Keep requested formats materially
   consistent, derived from the same content model or parity-checked; each must
   contain its reader-required substance, and Markdown may only point to HTML
   when HTML is explicitly the sole requested format. Add a report-quality eval,
   glossary, or figure/table guide only when selected or needed by that report.
   Include the actual artifact path in the final response or handoff.

## Closeout Tokens

When structured writeout closeout is needed, record completion evidence and only
the selected output paths; omit tokens for optional operations that did not run.
Use `result_writeout=complete` only after selected operations and required
readbacks succeed; do not report completion for failed or partial work.

```text
result_writeout=complete
result_source=<command-or-existing-artifact>
result_artifacts=<path-role-checksum-readback-record>
result_overwrite_policy=<append-only|unique-file|regenerate-from-source>
```
